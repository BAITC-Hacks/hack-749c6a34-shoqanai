# Sana AI — подключение OpenAI

## Включение

1. Скопируйте `.env.example` в `.env` в корне проекта.
2. В `.env` укажите свой ключ после `OPENAI_API_KEY=`. Не отправляйте ключ в чат и не добавляйте его в Git.
3. `OPENAI_MODEL=gpt-4o-mini` можно заменить на доступную вашему аккаунту модель с поддержкой Responses API и Structured Outputs.
4. Запустите `start.bat` или `python start.py` (Python 3.10+). После изменения `.env` перезапустите сервер.
5. В меню сайта откройте **Sana AI → Проверить подключение**. Этот запрос проверяет наличие конфигурации; доступность ключа, модели и лимита проверяется первым реальным запросом.

Подписка на чат и API могут иметь разные условия доступа. Для работы нужен действующий API-ключ с доступом к выбранной модели и доступным лимитом API.

## Два сценария

- **Конструктор:** «Помочь оформить» отправляет описание и поля задачи на сервер. Модель возвращает 3–9 уточняющих вопросов. Ответы остаются редактируемыми, публикация ручная. Если сервер или модель недоступны, сайт показывает причину и локальные вопросы.
- **Sana AI:** чат помогает сформулировать потребность, критерии успеха и план прототипа. По желанию можно включить текущий черновик как контекст. Ответы не изменяют карточку автоматически. При ошибке текст вопроса восстанавливается для повторной отправки. История чата хранится только до перезагрузки; модель получает последние 8 сообщений.

## Данные и архитектура

Браузер → `POST /api/ai` → `ai_server.py` → OpenAI Responses API.

Ключ читается только сервером. `.env` исключён из Git и не доступен через HTTP. Сервер отдаёт только разрешённые файлы интерфейса; листинг каталогов отключён. Он слушает только `127.0.0.1`, проверяет Host и Origin, ограничивает тело запроса (64 KB), параллельные обращения (2) и частоту (20 в минуту). Это локальный сервер MVP, не публичный production-сервис.

Поле `contact` и название компании не включаются в автоматически передаваемый контекст. Однако сведения, введённые в других полях или сообщении, отправляются провайдеру — не вводите туда конфиденциальные данные. Для запросов указан `store: false`; это не обещание отсутствия любого хранения со стороны провайдера.

Ответ модели проходит JSON Schema и дополнительную проверку на сервере и клиенте. Промпт расположен в `ai_server.py` (`PROMPT`), локальный промпт — в `domain.js`. Ошибки провайдера не раскрывают ключи и содержимое запроса.

Формат запроса: `{mode: "questions" | "chat", task: {...}, message: "...", history: [{role, content}]}`.
Формат ответа: `{source: "openai", message: "...", questions: [{field, question}]}`.

Реализация использует [Structured Outputs в Responses API](https://developers.openai.com/api/docs/guides/structured-outputs).

## Ограничения запуска

При открытии `index.html` напрямую, через обычный статический сервер или GitHub Pages API-маршрутов нет: конструктор использует локальные вопросы, чат показывает инструкцию подключения. Для публичного сайта потребуется размещённый backend с авторизацией и защитой расходования API-лимита.

## Проверки

```sh
python tests/test_ai_server.py
node tests/workflow.cjs
node tests/ai-client.cjs
```

Серверные тесты используют заглушку OpenAI: проверяют HTTP, отказ без ключа, Origin, приватные файлы, валидацию и ошибки провайдера. Они не расходуют API-лимит. Успешный живой запрос нужно проверить после добавления своего ключа.
